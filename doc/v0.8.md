# ruvm v0.8：速度（與誠實的結論）

目標原本是「開機時間降到 1/3」。結果沒有達到：目前純直譯器的上限大約 **110–130 MIPS**（真實 Linux 開機的指令組合），
這版只拿到約 10%。這份文件記錄量了什麼、試了什麼、哪些有效、哪些沒用，以及要再快需要什麼。

## 量測方法

* `tools/bench.sh`：ALU 迴圈與「Linux 開機前 30 億個指令」的 MIPS。
* macOS `sample` 對執行中的行程取樣，再用 `llvm-objdump` 把位址對回指令（`CARGO_PROFILE_RELEASE_DEBUG=1`
  另開 `--target-dir`，不影響正式建置）。注意：函式被內聯時行號會歸到呼叫者，所以要把 `exec` 設成 `#[inline(never)]`
  才看得到內部分佈。

| 工作負載 | v0.7 | v0.8 |
|---|---|---|
| riscv64 Linux 開機（30 億指令） | ~27 s（111 MIPS） | ~26 s（116 MIPS） |
| aarch64 Linux 開機（30 億指令） | ~28 s（107 MIPS） | ~23 s（128 MIPS） |

## 有效的改變

1. **AArch64 解碼依編碼大類分流**：`(insn >> 25) & 0xf` 先選 DP-immediate / 分支與系統 / 載入儲存 / DP-register / FP-SIMD，
   原本一條 37 個分支的 if/else 鏈變成每類 5–10 個測試。
2. **批次執行**（兩種架構）：板子時鐘、計時器、中斷線、halt 旗標每 32 個指令才檢查一次，而不是每個指令。
   為了保持與 QEMU 相同的語意，下列事件會**立刻結束批次**並重新檢查中斷：CSR／系統暫存器寫入、`mret`/`sret`/`eret`、
   `msr daif*`、任何裝置 MMIO 存取。批次提早結束時會把沒用掉的時間與 `instret` 還回去，所以計數仍然精確。
   （第一版沒做這件事，`rv_priv` 差分測試立刻抓到中斷慢了幾個指令才被接收。）
3. **MMU 熱路徑**：AArch64 的 TLB 項目預先算好 6 個權限位元（EL0/EL1 × 取指/讀/寫），命中只要一次位元測試；
   頁表遍歷標 `#[cold]`。邏輯立即數遮罩解碼加快取。小函式（`addsub`、`shift_val`、`cond`…）強制內聯。

## 試過但沒有幫助的

| 嘗試 | 結果 |
|---|---|
| 較大的 TLB（256→4096、1024→8192） | 無差異（而且每次 `sfence.vma` 清得更慢），已還原 |
| `-C target-cpu=native` | 無差異 |
| 把 `Result<_, Ex>` 的錯誤型別改成 `Box`（回傳值縮成兩個暫存器） | 無差異（保留，無害） |
| RVC 展開表改成放在 CPU 結構裡（去掉 `OnceLock`） | 無差異（保留） |
| RISC-V 批次化 | 只有中斷檢查變少，速度幾乎不變（正確性才是重點） |

## 瓶頸在哪

取樣顯示時間平均分散在 `exec` 的 prologue/epilogue、取指、`match` 派發與載入路徑，沒有單一熱點。
每個客體指令大約要 60–80 個主機指令，而且**只有一個共用的間接跳轉**（`match op` 編成跳轉表）會讓分支預測器很吃力。
Rust 沒有 computed goto 或保證的 tail call，所以直譯器沒辦法做「每個 handler 自己跳到下一個」的 threaded code。

## 要再快 2–5 倍需要什麼

* **預先解碼的指令區塊**（每個實體頁一個 `Vec<Op>`，指令只解碼一次，`Op` 帶預先取好的欄位），
  搭配 FENCE.I / `IC` / `SFENCE` 時失效；或
* **JIT**（把基本區塊編成主機機器碼）。

兩者都是大工程，而且 JIT 不能再「逐位元與 QEMU 比對」那麼容易驗證，所以留到 v1.0 之後。
目前的速度對教學與測試已足夠：RISC-V 約 25 秒、ARM 約 25–35 秒開機到 shell（用 v0.7 的小 initramfs）。
